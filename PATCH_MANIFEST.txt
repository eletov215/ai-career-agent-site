Reason for change:
  Complete AUTH-001 E2E on the current free staging infrastructure without paying for SMTP-capable Render compute. Gmail API uses HTTPS instead of SMTP and keeps the auth business logic provider-neutral.

Implementation:
  - add AUTH_EMAIL_BACKEND=gmail_api;
  - refresh OAuth access tokens over HTTPS from AUTH_GMAIL_REFRESH_TOKEN;
  - send RFC 2822 MIME messages as base64url through Gmail users.messages.send;
  - never persist a permanent access token;
  - keep SMTP STARTTLS and implicit SSL/TLS adapters unchanged for VPS/paid infrastructure;
  - add safe Gmail failure telemetry: stage + HTTP status + exception type only;
  - add mocked positive/negative Gmail API tests and include email-delivery tests in the dedicated AUTH-001 CI gate.

New environment values:
  AUTH_EMAIL_FROM
  AUTH_GMAIL_CLIENT_ID
  AUTH_GMAIL_CLIENT_SECRET
  AUTH_GMAIL_REFRESH_TOKEN
  AUTH_GMAIL_TIMEOUT_SECONDS

Security invariants:
  - Client Secret, Refresh Token and access tokens are never committed or logged;
  - provider response bodies are not logged;
  - external Google calls are mocked in CI;
  - production test-memory backend remains forbidden;
  - existing SMTP plaintext/conflicting-mode protections remain unchanged;
  - CSRF/session/password/token controls remain unchanged;
  - no migration.

Mandatory pre-release architecture decision:
  Gmail API is staging-only. Before beta/commercial release switch to a project-owned domain sender (target example noreply@ai-career-agent.ru) through production-grade transactional delivery with SPF/DKIM/DMARC. The email transport swap must not rewrite registration/verification/reset business logic.
